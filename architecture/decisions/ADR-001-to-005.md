# ADR-001: API Gateway and Web Framework Selection

## Status
Accepted

## Context
A ChatGPT-like application serving 1M users with heavy concurrent streaming workloads requires an API gateway layer capable of handling tens of thousands of concurrent long-lived HTTP connections (Server-Sent Events) with minimal event loop latency, low memory footprint per socket, and zero serialization overhead.

## Decision
We chose **Fastify** over Express.js and NestJS for the core API gateway and routing layer.

## Alternatives Considered
- **Express.js**: Standard Node.js framework, but suffers from higher memory consumption per connection, lacks native schema validation, and has significantly lower throughput under concurrent SSE streaming.
- **NestJS**: Provides strict OOP architecture, but introduces heavy abstraction overhead and dependency injection layers that increase cold start times and latency.
- **Go / Rust**: Extremely fast, but TypeScript across both backend and frontend enables single-language full-stack type sharing, rapid iteration, and shared schema validation (Zod).

## Trade-offs & Consequences
- **Pros**:
  - 2x-3x higher requests/sec and lower latency than Express.
  - Built-in schema compilation with fast-json-stringify.
  - Clean async/await plugin ecosystem.
  - Low memory footprint (~30MB base runtime).
- **Cons**:
  - Smaller middleware ecosystem compared to legacy Express (easily mitigated via `@fastify/express` if needed).

# ADR-002: Relational Persistence with PostgreSQL

## Status
Accepted

## Context
Conversational AI systems require persistence for users, organizational tenants, conversation threads, message histories, token usage audits, and billing records. The data is inherently structured with strict relational integrity (users -> conversations -> messages -> usage records).

## Decision
We chose **PostgreSQL 16** as the primary relational system of record, combined with Redis for hot cache tiers and read replicas for horizontal query scaling.

## Alternatives Considered
- **MongoDB / DocumentDB**: Flexible schema, but lacks ACID transactional guarantees for multi-tenant billing/usage records and requires manual reference integrity management.
- **DynamoDB / Cassandra**: Excellent partition write scaling, but complex query patterns (e.g. searching user conversations by model, date ranges, token audits) require expensive secondary indexes.

## Scaling Strategy
- **Partitioning**: Partition the `messages` and `model_requests` tables by `created_at` (monthly partitions) to maintain fast index traversal as data grows past 100M+ rows.
- **Read Replicas**: Direct all read-heavy history fetching (`GET /api/conversations`) to read replicas, preserving the primary master for conversational write streaming.

# ADR-003: Redis for Ephemeral State, Caching, and Rate Limiting

## Status
Accepted

## Context
High-frequency operations such as token-bucket rate limiting (RPM/TPM), active concurrency tracking, session caching, and prompt prefix metadata must be processed in sub-millisecond latencies without stressing the relational database.

## Decision
We chose **Redis 7 Cluster** to power:
1. Distributed Sliding Window Rate Limiting (RPM, TPM, Concurrency).
2. Hot conversation metadata caching.
3. Request deduplication & Idempotency leases.
4. Temporary circuit breaker telemetry state.

## Trade-offs & Consequences
- **Pros**:
  - Sub-millisecond read/write latency.
  - Native atomic primitives (`INCRBY`, `EXPIRE`, Lua scripts) ensure race-condition-free rate limiting.
- **Cons**:
  - In-memory data store requires careful TTL management to avoid memory exhaustion at 1M+ users.

# ADR-004: Server-Sent Events (SSE) vs WebSockets for Token Streaming

## Status
Accepted

## Context
LLM text generation produces tokens incrementally over several seconds. The client interface must render tokens with minimum Time-To-First-Token (TTFT) and seamless backpressure.

## Decision
We chose **Server-Sent Events (SSE)** over WebSockets and gRPC-Web for client-facing response streaming.

## Alternatives Considered
- **WebSockets**: Full duplex bidirectional channel. However, chat turns are fundamentally unidirectional streaming per prompt (Client sends 1 POST request -> Server streams N tokens). WebSockets bypass HTTP/2 multiplexing, complicate CDN/edge caching, and require custom ping/pong connection heartbeat state machines.
- **gRPC-Web**: Excellent binary protocol, but adds significant client bundling overhead and protobuf decoding complexity in browsers.

## Trade-offs & Consequences
- **Pros**:
  - Native HTTP/2 multiplexing over standard HTTPS (port 443).
  - Works transparently across corporate firewalls, CDNs, and proxies.
  - Automatic reconnection handling built into the EventSource browser API.
  - Simpler load balancing across stateless API containers.
- **Cons**:
  - Unidirectional (client can only send input at connection initiation; cancellation is handled via HTTP connection abort or separate DELETE/POST signals).

# ADR-005: Dynamic Multi-Tier Model Routing

## Status
Accepted

## Context
In a 1M-user platform, routing every prompt to a top-tier frontier model (e.g. 70B+ or reasoning model) is cost-prohibitive ($10+/M tokens) and introduces unnecessary latency for simple queries.

## Decision
We implemented a **Dynamic Model Router** with three tiers:
1. **Simple / Fast Tier**: 8B parameter class (e.g. Llama-3-8B / GPT-4o-mini) for lightweight queries, summarization, and greetings ($0.15/1M tokens, ~120ms TTFT).
2. **Standard Tier**: 70B parameter class for intermediate coding and knowledge tasks ($0.80/1M tokens, ~280ms TTFT).
3. **Reasoning Tier**: Deep thinking / chain-of-thought models for complex mathematical proofs, formal verification, and multi-step system design ($2.50/1M tokens).
4. **Resilient Circuit Breaker Fallback**: Automatically downgrades requests to secondary tiers if the primary provider trips circuit breakers.

## Trade-offs & Consequences
- **Pros**:
  - Reduces blended inference costs by up to 70%.
  - Improves average user latency by serving 60%+ of queries on fast models.
  - Eliminates single points of failure via automatic circuit-breaker fallback.
